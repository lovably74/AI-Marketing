# 협업 업무분장 — T-LINK AI Marketing Studio

| 항목 | 내용 |
|---|---|
| 문서번호 | A19-PM-001 |
| 버전 | v0.1 |
| 작성일 | 2026-11-20 |
| 작성 | Claude (개발자 A 세션, PM) |

두 명의 개발자가 각자 Claude Code로 협업한다. Claude의 메모리와 대화 맥락은 개발자 사이에 공유되지 않으므로, **모든 결정과 규칙은 저장소 안 문서**(루트 `CLAUDE.md`, PRD, ADR, 이 문서)를 기준으로 삼는다.

## 1. 분장 원칙
1. **계약을 기준으로 나눈다.** AI 응답 타입(`studio/src/lib/ai/schema.ts`)과 지식베이스·가이드라인 JSON(`studio/data/*.json`)이 두 영역의 경계다. 계약은 개발자 A가 소유하고, B는 읽기만 한다. 변경이 필요하면 A에게 요청한다.
2. **파일 단위로 소유자를 정한다.** 같은 파일을 두 사람이 동시에 고치지 않는다.
3. **골격이 push된 뒤 B가 착수한다.** 현재 A 세션이 `studio/` 골격(P0 전체)을 생성 중이며, 완료 후 main에 push하면 B가 pull해 시작한다.
4. **구현과 검증을 교차한다.** A의 결과는 B가, B의 결과는 A가 리뷰한다(Gitea PR 리뷰).

## 2. 역할과 소유 범위

| 구분 | 개발자 A (AI 파이프라인 + PM) | 개발자 B (출력물·관리·시험) |
|---|---|---|
| 책임 | 요구사항·PRD·ADR 관리, AI 분석 품질, 통합, main 머지 | 카드뉴스, 관리자 페이지, 시험·시연, Word 산출물 |
| 소유 코드 | `studio/src/lib/ai/**`, `studio/src/app/api/generate/**`, `studio/data/**`, 입력 화면과 결과 A·B 영역 | 카드뉴스 컴포넌트(결과 C 영역, PNG 다운로드), `studio/src/app/admin/**`, `studio/src/app/api/models/**`, `studio/config/ai-models.json` |
| 소유 문서 | `docs/deliverables/PRD_요구사항정의서.md`, `docs/adr/**`, 현업무분석서, 이 문서 | `docs/deliverables/시험결과서.md`(신규), `docs/산출물/**`(Word 변환), `studio/README.md`의 시연 절차 절 |
| 주요 작업 | ① 실제 API 키로 Gemini/OpenAI 호출 검증 ② 프롬프트 튜닝(가이드라인 준수율, 근거 ID 정확도) ③ 검증 로직(금지 표현, 키워드) 보강 ④ 오류 처리 | ① 카드뉴스 디자인 고도화(브랜드 컬러, 한글 줄바꿈, 넘침 방지, PNG 폰트 누락 확인) ② 관리자 페이지 마무리와 연결 테스트(P2) ③ 시험 사진 세트 준비(사무실·콜센터·외근 영업 등, 개인정보 없는 것) ④ 완료기준 1~10 통합시험과 시험결과서 ⑤ md → Word 변환 |
| 공유 파일(수정 전 상대에게 알림) | `studio/src/app/page.tsx`(화면 배치), `studio/package.json`(의존성 추가), 루트 `CLAUDE.md` | 동일 |

> 둘 다 손대야 하는 `page.tsx`는 A가 소유하고, B는 카드뉴스를 별도 컴포넌트 파일로 만들어 `page.tsx`에는 한 줄로만 연결한다.

## 3. 형상관리 규칙 (Gitea: roigitadmin/AI-Marketing)
- 브랜치: `main`은 항상 빌드 가능한 상태로 유지한다. 작업은 `feature/a-<주제>`, `feature/b-<주제>`에서 하고 Gitea PR로 병합한다.
- 작업 전 `git pull`(main 최신화 후 내 브랜치에 반영), 작업 후 내가 바꾼 파일만 커밋하고 push한다. force push와 히스토리 재작성은 금지한다.
- 커밋 메시지는 한글로 쓰고 무엇을, 왜 바꿨는지 적는다.
- PR 병합 조건: `npm run build`와 `npm run lint` 성공, 상대 개발자(또는 상대의 Claude)가 리뷰.
- `.env.local`과 API 키는 절대 커밋하지 않는다. 키는 각자 발급하거나 안전한 경로로 따로 전달한다.

## 4. 동기화 지점
| 시점 | 내용 |
|---|---|
| 골격 push 직후 | A가 B에게 착수를 알림. B는 `CLAUDE.md`, PRD, 이 문서를 읽고 시작 |
| 계약 변경 시 | A가 `schema.ts`와 지식베이스를 바꾸면 PR 설명에 영향 범위(카드뉴스 필드 등)를 적는다 |
| 통합시험 전 | 두 브랜치 모두 main에 병합 → B가 완료기준 1~10 시험 → 결함은 시험결과서에 기록 후 소유자가 수정 |
| 시연 전 | README 시연 절차로 리허설(B), 실제 API 호출 확인(A) |

## 5. 리스크
| 리스크 | 대응 |
|---|---|
| 두 Claude가 서로 다른 기준으로 작업 | 루트 `CLAUDE.md`에 프로젝트 규칙을 명시한다. 결정은 PRD·ADR에만 기록하고, 개인 메모리에만 남기지 않는다 |
| `page.tsx`, `package.json` 충돌 | 소유자를 정하고, 수정 전에 알리고, 작은 PR을 자주 올린다 |
| API 키 한 개를 공유해 비용·한도 초과 | 개발자별로 키를 따로 쓴다 |
| 3시간 일정 | 각자 P0 → P1 순서를 지키고, 디자인 고도화는 P0 통합시험을 통과한 뒤에 한다 |
